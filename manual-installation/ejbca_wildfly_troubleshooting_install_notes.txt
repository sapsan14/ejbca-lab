EJ B C A 9.2.0 (eIDAS) + WildFly 35 — установка и отладка (JNDI, mTLS для AdminWeb, Elytron/keystores)
====================================================================================

Цель
----
Довести стенд до состояния, когда:
1) EJBCA развернут на WildFly и доступен по https://localhost:8443/ejbca/…
2) CLI EJBCA (bin/ejbca.sh) работает без JNDI-ошибок на базовых командах (например, ca listcas).
3) Страница AdminWeb (…/ejbca/adminweb/) требует клиентский сертификат и принимает SuperAdmin.p12.
4) Конфигурация WildFly (Elytron) корректно доверяет ManagementCA и запрашивает mTLS.

Версии и пути (пример стенда)
-----------------------------
- ОС: Ubuntu
- Java: 17
- WildFly: /opt/wildfly (Standalone; конфигурация — standalone-full.xml)
- EJBCA: /opt/ejbca/src/ejbca_ee_9_2_0_eIDAS
- HTTPS-порт: 8443 (standalone сокет “https”)
- Логи WildFly: /opt/wildfly/standalone/log/server.log
- Деплой: /opt/wildfly/standalone/deployments/ejbca.ear
- AdminWeb контекст: /ejbca/adminweb
- RA контекст: /ejbca/ra

Переменные окружения
--------------------
(под пользователем ejbca)
export EJBCA_HOME="/opt/ejbca/src/ejbca_ee_9_2_0_eIDAS"
export PATH="/opt/wildfly/bin:$PATH"

-------------------------
1) Убедиться, что ejbca.ear задеплоирован:
   ls -l /opt/wildfly/standalone/deployments

   Ожидается:
   - ejbca.ear
   - ejbca.ear.deployed

2) Проверка логов WildFly (без sudo, если владелец — ejbca):
   tail -n 200 /opt/wildfly/standalone/log/server.log

   На успешный деплой указывают строки:
   - “Registered web context: '/ejbca/ra' …”
   - “Registered web context: '/ejbca/adminweb' …”
   - “Deployed "ejbca.ear" …”
   - “WildFly … started in … Server configuration file in use: standalone-full.xml …”

3) Базовая проверка HTTPS-листенера (увидите welcome WildFly на корне /):
   curl -vk https://localhost:8443/

Проверка CLI EJBCA и устранение JNDI-ошибок
-------------------------------------------
Симптом:
- При вызове некоторых команд возникала ошибка:
  javax.naming.NoInitialContextException: Need to specify class name in environment … java.naming.factory.initial
  или
  ClassNotFoundException: org.wildfly.naming.client.WildFlyInitialContextFactory

Причина и решение:
- Эти ошибки возникают, когда CLI пытается создавать удаленные EJB-клиенты, а окружение/класс-пути не совпадают.
- Для большинства базовых локальных команд jndi не требуется. Не задавайте вручную -Djava.naming.*, если не добавляете зависимости wildfly-naming-client.
- Используйте штатный скрипт bin/ejbca.sh без внешних jndi-настроек; проверьте, что EJBCA_HOME верен и существует dist/ejbca-ejb-cli/ejbca-ejb-cli.jar.

Полезные проверки:
- Показать категории CLI:
  bin/ejbca.sh --help
  bin/ejbca.sh version   (должно вывести список категорий/команд)

- Список CA (доказывает доступ к базе и инициализацию ManagementCA):
  bin/ejbca.sh ca listcas
  Пример ожидаемого:
  CA Name: ManagementCA
   Id: 1652389506
   Issuer DN: CN=ManagementCA,O=EJBCA Sample,C=SE
   Subject DN: CN=ManagementCA,O=EJBCA Sample,C=SE
   …

Инициализация ManagementCA и SuperAdmin (замечания)
---------------------------------------------------
- В рамках “ant runinstall” (интерактивный) могла быть создана ManagementCA и SuperAdmin.p12.
- Файл SuperAdmin.p12 обычно обнаруживается тут:
  /opt/ejbca/src/ejbca_ee_9_2_0_eIDAS/p12/superadmin.p12

- Проверка содержимого p12 (без ключа):
  openssl pkcs12 -info -in /opt/ejbca/src/ejbca_ee_9_2_0_eIDAS/p12/superadmin.p12 -nokeys

- Извлечение лишь CA-сертификата из p12 (понадобится для truststore WildFly):
  openssl pkcs12 -in /opt/ejbca/src/ejbca_ee_9_2_0_eIDAS/p12/superadmin.p12     -nokeys -cacerts -out /opt/wildfly/standalone/configuration/managementca.pem

  Проверка результата:
  openssl x509 -in /opt/wildfly/standalone/configuration/managementca.pem -noout -subject -issuer -enddate
  Ожидается self-signed CN=ManagementCA … notAfter=…2035 …

Задача: добиться mTLS на AdminWeb (чтобы браузер попросил клиентский сертификат)
-------------------------------------------------------------------------------
По умолчанию https-listener использует ssl-context=applicationSSC, у которого need-client-auth=false.
Попытка просто “verify-client=REQUIRED” на listener падает:
  WFLYCTL0105: ssl-context is invalid in combination with verify-client

Правильный путь:
1) Импортировать ManagementCA в локальный truststore (PKCS12/JKS).
2) Создать в Elytron key-store, trust-manager, server-ssl-context с need-client-auth=true.
3) Назначить этот ssl-context https-listener’у.

Шаг A. Создаем локальный truststore из PEM (один раз)
-----------------------------------------------------
cd /opt/wildfly/standalone/configuration

keytool -importcert   -keystore managementca.jks   -storepass changeit   -alias managementca   -file /opt/wildfly/standalone/configuration/managementca.pem   -noprompt

Проверка:
keytool -list -v -keystore managementca.jks -storepass changeit
Ожидается тип PKCS12, один trustedCertEntry с CN=ManagementCA …

Шаг B. Регистрируем этот truststore в Elytron как key-store
-----------------------------------------------------------
/opt/wildfly/bin/jboss-cli.sh --connect   --command="/subsystem=elytron/key-store=managementCAKS:add(       path=managementca.jks,       relative-to=jboss.server.config.dir,       type=PKCS12,       credential-reference={clear-text=changeit})"

Если “already exists” — значит узел уже создан.

Шаг C. Создаем trust-manager на основе key-store
------------------------------------------------
/opt/wildfly/bin/jboss-cli.sh --connect   --command="/subsystem=elytron/trust-manager=managementTM:add(       key-store=managementCAKS, algorithm=PKIX)"

Шаг D. Создаем новый server-ssl-context с проверкой клиента
-----------------------------------------------------------
В качестве key-manager используем “applicationKM” (он указывает на applicationKS с server-cert “CN=localhost”).
need-client-auth=true заставляет сервер требовать клиентский сертификат.

/opt/wildfly/bin/jboss-cli.sh --connect   --command="/subsystem=elytron/server-ssl-context=managementSSC:add(       key-manager=applicationKM,       trust-manager=managementTM,       need-client-auth=true)"

Шаг E. Назначаем наш новый ssl-context https-listенеру
------------------------------------------------------
/opt/wildfly/bin/jboss-cli.sh --connect   --command="/subsystem=undertow/server=default-server/https-listener=https:write-attribute(name=ssl-context,value=managementSSC)"

Шаг F. Перезапуск WildFly
-------------------------
Вариант 1 (systemd):
sudo systemctl restart wildfly

Вариант 2 (через CLI):
/opt/wildfly/bin/jboss-cli.sh --connect --command="shutdown --restart=true"

Проверки после включения mTLS
-----------------------------
1) CURL без клиентского сертификата должен получить страницу “Authorization Denied / No client certificate was presented” (HTTP 200 с текстом):
   curl -vk https://localhost:8443/ejbca/adminweb/

2) CURL с клиентским сертификатом SuperAdmin.p12 должен пройти дальше (и больше не видеть “No client certificate was presented”):
   cd /opt/ejbca/src/ejbca_ee_9_2_0_eIDAS/p12

   curl -vk      --cert superadmin.p12:ejbca --cert-type P12      https://localhost:8443/ejbca/adminweb/

   (Пароль к P12 — тот, который задавался при установке/генерации. В примерах — “ejbca”.)

3) В браузере:
   - Импортировать superadmin.p12 в хранилище браузера.
   - Зайти на https://localhost:8443/ejbca/adminweb/ — должен появиться диалог выбора сертификата.
   - После выбора SuperAdmin — доступ к консоли AdminWeb.

Диагностика, если нет запроса клиентского сертификата
-----------------------------------------------------
- Проверить, какой ssl-context у https-listенера:
  /opt/wildfly/bin/jboss-cli.sh --connect     --commands="/subsystem=undertow/server=default-server:read-children-resources(child-type=https-listener, include-runtime=true, recursive=true)"
  Должно быть "ssl-context" => "managementSSC" и "verify-client" можно оставить NOT_REQUESTED (управляет SSL контекст).

- Проверить Elytron конфигурацию (ключевые узлы):
  /opt/wildfly/bin/jboss-cli.sh --connect     --commands="/subsystem=elytron:read-resource(recursive=true)"
  Ищем:
    key-store=managementCAKS (path=managementca.jks, type=PKCS12)
    trust-manager=managementTM (key-store=managementCAKS)
    server-ssl-context=managementSSC (key-manager=applicationKM, trust-manager=managementTM, need-client-auth=true)

- Логи на стороне AdminWeb при отсутствии аутентификации:
  tail -n 200 /opt/wildfly/standalone/log/server.log
  Типичное сообщение:
  org.cesecore.authentication.AuthenticationNotProvidedException: Client certificate or OAuth bearer token required.

Полезные команды для инспекции https-listenера
----------------------------------------------
/opt/wildfly/bin/jboss-cli.sh --connect   --commands="/subsystem=undertow/server=default-server:read-children-resources(child-type=https-listener, include-runtime=true, recursive=true)"

(Покажет ssl-context, enable-http2, socket-binding=https, и т.д.)

Замечания по “verify-client” vs “need-client-auth”
--------------------------------------------------
- В Undertow (WildFly 35) корректнее управлять запросом клиентского сертификата через Elytron server-ssl-context: need-client-auth=true.
- Попытка напрямую установить verify-client=REQUIRED на https-listener при ssl-context=applicationSSC приводит к ошибке:
  WFLYCTL0105: ssl-context is invalid in combination with verify-client
- Поэтому создается отдельный server-ssl-context (managementSSC) с need-client-auth=true и trust-manager’ом.

Типовые проблемы и краткие решения
----------------------------------
1) “JNDI name lookup error / NoInitialContextException” при запуске CLI:
   - Не указывайте вручную -Djava.naming.factory.initial без добавления нужных wildfly-naming-client зависимостей.
   - Для базовых команд используйте штатный bin/ejbca.sh и убедитесь в корректности EJBCA_HOME и наличия dist/ejbca-ejb-cli/ejbca-ejb-cli.jar.
   - Некоторые команды (keybind и др.) требуют работающего контейнера/доступа к EJB — смотрите логи WildFly.

2) “No client certificate was presented” в AdminWeb:
   - Значит не настроено mTLS на https-listенере. Выполните шаги A–F (truststore, Elytron key-store/trust-manager, server-ssl-context, назначение ssl-context, рестарт).

3) “WFLYCTL0105: ssl-context is invalid in combination with verify-client”:
   - Не меняйте verify-client у listener’а напрямую; создайте правильный Elytron server-ssl-context с need-client-auth=true и подмените ssl-context у listener’а.

4) Видите только “Welcome to WildFly” на https://localhost:8443/:
   - Это корень контейнера. Страницы EJBCA по путям:
     https://localhost:8443/ejbca/adminweb/
     https://localhost:8443/ejbca/ra/

5) Где искать superadmin.p12:
   - /opt/ejbca/src/ejbca_ee_9_2_0_eIDAS/p12/superadmin.p12
